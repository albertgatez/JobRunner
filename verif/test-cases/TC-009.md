# TC-009 — Cierre controlado sin procesos huérfanos

## 1. Identificación

| Campo | Valor |
|---|---|
| ID | TC-009 |
| Título | Cierre controlado del servidor y terminación de grupos de procesos |
| Requisitos relacionados | RF-15, RNF-25, RNF-30 |
| Tipo | System |
| Método | TEST |
| Prioridad | Alta |
| Estado | PASS |
| Script | `verif/scripts/tc-009.sh` |

## 2. Objetivo

Verificar que `SIGINT` y `SIGTERM` cierren el servidor de forma controlada, que los Jobs en ejecución reciban `SIGTERM` y que los procesos que lo ignoran reciban `SIGKILL`. Los Jobs en cola deben permanecer sin ejecutarse y el servidor no debe dejar procesos del grupo vivos.

## 3. Precondiciones y entorno

- Linux con `bash`, `python3`, `ps`, `awk`, `pgrep`, `kill` y `grep`.
- Ejecutables `jobrunner-server` y `jobrunner-cli` recién compilados con CMake.
- El script crea una base SQLite temporal, un socket de prueba y sus propios procesos.
- El servidor usa un límite de 3 Jobs simultáneos; el cuarto Job queda en cola.

## 4. Procedimiento y resultados esperados

### Caso A — Cierre con Jobs que responden a `SIGTERM`

1. Iniciar el servidor y enviar cuatro Jobs `sleep`.
2. Confirmar que tres procesos están en ejecución y el cuarto no se lanzó.
3. Enviar `SIGINT` al servidor.
4. Confirmar código de salida 0, cierre en menos de 4 s, desaparición de los tres procesos, conservación del Job en cola y eliminación del socket.

### Caso B — Job que ignora `SIGTERM`

1. Iniciar el servidor y enviar un Job que ignore `SIGTERM`.
2. Enviar `SIGTERM` al servidor.
3. Confirmar que el servidor espera durante el plazo de gracia (4–8 s), registra el escalamiento a `SIGKILL` y termina sin procesos del grupo vivos.

### Caso C — Subproceso que ignora `SIGTERM`

1. Iniciar el servidor y enviar un Job cuyo subproceso ignora `SIGTERM`.
2. Enviar `SIGINT` al servidor.
3. Confirmar que el grupo completo desaparece, incluso si el proceso líder termina antes que el subproceso.

## 5. Criterios de aceptación

- El servidor termina con código 0 en los tres casos.
- Ningún grupo del Job deja procesos vivos tras el cierre.
- Los Jobs `QUEUED` no se despachan durante el cierre.
- El escalamiento a `SIGKILL` ocurre al vencer el plazo de gracia, no de inmediato.
- Se ejecutan las 15 comprobaciones definidas por el script y todas pasan.
