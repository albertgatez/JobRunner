## 2. Objetivo

Verificar que el servidor acepta solicitudes de envío válidas, devuelve un identificador único por cada Job distinto, rechaza con un mensaje de error las solicitudes inválidas y sigue atendiendo solicitudes después de recibirlas.

---

## 3. Requisitos a verificar

### RF-01 — Recepción de solicitudes de creación de Jobs

El servidor recibe solicitudes para crear Jobs y responde con un identificador.

### RF-02 — Validación de solicitudes

Network/API valida el formato de la solicitud y Job Manager valida su contenido (por ejemplo, comando vacío).

---

## 4. Precondiciones

-  JobRunner está compilado (`cmake -S . -B build && cmake --build build`).
-  El servicio está configurado correctamente (ruta de socket de prueba, p. ej. `/tmp/jobrunner-tc001.sock`).
-  La configuración requerida está disponible (en Avance 1 solo la ruta del socket).
-  Los archivos de prueba están preparados (`python3` disponible para el paso de tramas crudas).
-  No existen procesos `jobrunner-server` de pruebas anteriores ejecutándose.

## 6. Datos de prueba

### Entrada

```text
submit echo hola
submit echo adios          (distinto del anterior para no caer en la ventana de duplicados de 3 s, RF-27)
submit ""                  (comando vacío)
trama con JSON mal formado
trama JSON sin el campo "op"
```

### Configuración relevante

```text
Socket: /tmp/jobrunner-tc001.sock
```

### Condiciones especiales

Un solo cliente. Las tramas inválidas se envían con un script que arma el prefijo de longitud de 4 bytes big-endian seguido del contenido.

---

## 7. Procedimiento

### Paso 1

**Acción:**

Iniciar el servidor: `./build/jobrunner-server /tmp/jobrunner-tc001.sock`.

**Resultado esperado:**

El servidor queda escuchando y el socket existe.

---

### Paso 2

**Acción:**

`./build/jobrunner-cli /tmp/jobrunner-tc001.sock submit echo hola`

**Resultado esperado:**

Respuesta `ok: true` con un `job_id` numérico; código de salida del cliente 0.

---

### Paso 3

**Acción:**

`./build/jobrunner-cli /tmp/jobrunner-tc001.sock submit echo adios`

**Resultado esperado:**

Respuesta `ok: true` con un `job_id` distinto al del paso 2.

---

### Paso 4

**Acción:**

`./build/jobrunner-cli /tmp/jobrunner-tc001.sock submit ""`

**Resultado esperado:**

Respuesta `ok: false` con mensaje de error; código de salida del cliente distinto de 0; no se crea ningún Job nuevo (`list` no cambia).

---

### Paso 5

**Acción:**

Enviar por socket una trama con JSON mal formado y otra con JSON válido sin el campo `op`.

**Resultado esperado:**

Cada una recibe `ok: false` con mensaje de error.

---

### Paso 6

**Acción:**

Repetir el paso 2 con un comando distinto (`submit echo final`) y comprobar que el proceso del servidor sigue vivo (`kill -0 <pid>`).

**Resultado esperado:**

El servidor responde `ok: true` y sigue en ejecución.

---

## 8. Resultado esperado

-  Los envíos válidos devuelven `ok: true` y un `job_id`.
-  Los `job_id` de Jobs distintos son distintos.
-  Comando vacío, JSON mal formado y operación faltante devuelven `ok: false` con mensaje.
-  El servidor sigue respondiendo después de las solicitudes inválidas.

**Criterio para PASS:**

Se cumplen los cuatro criterios anteriores y la evidencia queda guardada en `verif/results/<run-id>/`.

**Criterio para FAIL:**

El servidor termina, no responde, repite un `job_id` entre Jobs distintos o acepta una solicitud inválida.
