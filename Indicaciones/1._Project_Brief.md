# JobRunner — Project Brief

## Propósito
El cliente requiere una plataforma ligera para registrar, ejecutar, supervisar y controlar trabajos del sistema operativo en equipos Linux. El producto deberá demostrar programación de sistemas: procesos, señales, concurrencia, comunicación entre procesos, persistencia básica y comunicación en red.

## Objetivo del producto
Entregar un JobRunner operativo que permita enviar comandos o programas como trabajos, ejecutarlos en segundo plano con concurrencia controlada, consultar su estado, recuperar su salida y solicitar su terminación. El servicio deberá admitir operación local y acceso remoto únicamente desde la misma red privada o mediante VPN.

## Usuarios y partes interesadas
- Usuario operador: envía y controla trabajos. 
- Administrador: configura límites y acceso de red. 
- Cliente académico: revisa cumplimiento, evidencia y calidad de ingeniería. 
- Equipo de desarrollo: diseña, implementa, verifica y mantiene el producto.

## Alcance incluido
- Servicio JobRunner para Linux
- Cliente de línea de comandos
- Cola y ciclo de vida de trabajos
- Ejecución concurrente
- Captura de `stdout`/`stderr`
- Consulta, listado y cancelación
- Persistencia mínima de metadatos
- Bitácora
- Interfaz de red privada
- Documentación, pruebas y evidencia reproducible.

## Fuera de alcance
Ejecución a través de Internet público; interfaz web obligatoria; orquestación de contenedores; alta disponibilidad; facturación; ejecución distribuida entre múltiples servidores; autenticación empresarial. Cualquier ampliación deberá registrarse como alcance opcional.
> Los elementos indicados como “fuera de alcance” no son obligatorios y no formarán parte de la evaluación base. En particular, JobRunner no requiere una interfaz web: la interacción mediante cliente de línea de comandos es suficiente.
El equipo podrá proponer funciones adicionales, como una interfaz web o el uso de contenedores, únicamente después de cumplir los requisitos obligatorios. Estas ampliaciones deberán documentarse como opcionales y no podrán sustituir, modificar ni retrasar las funciones requeridas del sistema.

## Restricción de red
- El servicio remoto deberá escuchar en una dirección configurable y aceptar conexiones solo desde localhost, la LAN autorizada o una VPN.
- No se permite exponerlo directamente a Internet.
- La demostración deberá incluir conexión permitida y conexión rechazada o bloqueada.

## Supuestos
- Sistema objetivo Linux
- Herramientas libres disponibles
- Equipos en una red controlada
- Tamaño de carga académico
- Los comandos ejecutados pertenecen al usuario del servicio y no requieren privilegios elevados

## Criterio de éxito
El producto se considera exitoso cuando satisface los requisitos aprobados:
1. Supera la verificación formal.
2. Demuestra utilidad ante escenarios de usuario y puede ser instalado.
3. Operado y reproducido por un tercero con la documentación entregada.

## Control de cambios
Toda ambigüedad, excepción o cambio de alcance deberá documentarse en un Issue y aprobarse antes de modificar la línea base de requisitos.

## Responsabilidad técnica del proveedor
El cliente define las capacidades y restricciones observables del producto, pero no prescribe una arquitectura única.
- El equipo proveedor deberá tomar, documentar, verificar y defender las decisiones necesarias para satisfacer los requisitos.
- Elegir y justificar el lenguaje, arquitectura, modelo de concurrencia, IPC, persistencia, protocolo y estrategia de recuperación.
- Comparar al menos dos alternativas viables para cada decisión arquitectónica relevante.
- Registrar consecuencias, riesgos y evidencia técnica de la alternativa elegida.
- Conservar trazabilidad entre decisiones, requisitos, implementación y pruebas.

## Uso de herramientas de inteligencia artificial
- El uso de herramientas de inteligencia artificial y vibe coding está permitido. Sin embargo, ningún resultado generado se considerará evidencia de competencia por sí mismo.
- El equipo será responsable de comprender, revisar, adaptar y probar todo artefacto entregado.
- La frase “lo recomendó la IA” no constituye una justificación técnica.
- Durante las revisiones, cualquier integrante podrá ser requerido para explicar una decisión, diagnosticar una falla o realizar un cambio limitado.
- El código que el equipo no pueda defender o verificar se considerará trabajo no terminado.
- Nota: la finalidad no es restringir el uso de IA, sino evaluar la capacidad del equipo para ejercer criterio y asumir responsabilidad técnica.
