# JobRunner — Requisitos Funcionales

## Convención
Cada requisito usa un identificador estable - RF-XX. “Deberá” indica obligación contractual. Cada RF deberá vincularse con uno o más casos de verificación y evidencia.

## Gestión de trabajos
- RF-01. El sistema deberá aceptar el envío de un comando o programa con sus argumentos y devolver un identificador único de trabajo.
- RF-02. El sistema deberá validar la solicitud y rechazar entradas vacías, mal formadas o no autorizadas con un mensaje útil.
- RF-03. El sistema deberá mantener una cola cuando no exista capacidad inmediata de ejecución.
- RF-04. El sistema deberá ejecutar trabajos en procesos separados sin bloquear la atención de nuevas solicitudes.
- RF-05. El sistema deberá permitir configurar un máximo de trabajos simultáneos y respetarlo.

## Ciclo de vida y control
- RF-06. El sistema deberá representar, como mínimo, los estados QUEUED, RUNNING, SUCCEEDED, FAILED y CANCELED.
- RF-07. El sistema deberá registrar tiempos de recepción, inicio y terminación, además del código de salida cuando aplique.
- RF-08. El usuario deberá poder consultar el estado y metadatos de un trabajo por su ID.
- RF-09. El usuario deberá poder listar trabajos con filtros básicos por estado.
- RF-10. El usuario deberá poder solicitar la cancelación de un trabajo en cola o en ejecución; el sistema deberá reflejar el resultado.

## Salida, persistencia y recuperación
- RF-11. El sistema deberá capturar stdout y stderr sin mezclarlos y permitir su consulta.
- RF-12. El sistema deberá conservar metadatos y resultados mínimos después de reiniciar el servicio.
- RF-13. Al arrancar, el sistema deberá recuperar el historial persistido y marcar coherentemente los trabajos interrumpidos.
- RF-14. El sistema deberá producir una bitácora de eventos operativos y errores con marca temporal e identificador de trabajo.

## Operación y configuración
- RF-15. El servicio deberá iniciar y detenerse de forma controlada, sin aceptar trabajos nuevos durante el cierre.
- RF-16. La configuración deberá permitir definir directorio de datos, límite de concurrencia, interfaz y puerto de escucha.
- RF-17. El cliente deberá ofrecer ayuda de uso y códigos de salida adecuados para éxito y error.

## Acceso remoto privado
- RF-18. Un cliente en otro equipo deberá poder enviar, consultar, listar y cancelar trabajos mediante un protocolo documentado.
- RF-19. El servicio deberá admitir operación local y remota sin cambiar la semántica de las operaciones.
- RF-20. El servicio deberá restringir el acceso remoto a una lista configurable de redes o direcciones permitidas de la LAN/VPN.
- RF-21. El protocolo deberá delimitar mensajes, identificar errores y tolerar lecturas o escrituras parciales.
- RF-22. El sistema deberá manejar desconexiones del cliente sin terminar el servicio ni corromper trabajos.

## Administración mínima
- RF-23. El servicio deberá rechazar solicitudes que excedan límites configurados y registrarlas.
- RF-24. El administrador deberá poder consultar un resumen de salud: servicio activo, trabajos en ejecución, en cola y errores recientes.

## Reglas de aceptación
Un requisito funcional solo se considera cumplido si existe implementación, caso de prueba, resultado esperado, evidencia y estado PASS en la matriz de trazabilidad. Una demostración manual sin evidencia reproducible no sustituye la prueba.


## Condiciones operativas y situaciones de conflicto
Los siguientes requisitos definen resultados observables. El equipo deberá decidir y justificar el mecanismo técnico utilizado para cumplirlos.
- RF-25. Cuando la cola alcance su capacidad configurada, el sistema deberá rechazar nuevas solicitudes de forma explícita, sin bloquear indefinidamente ni perder trabajos aceptados.
- RF-26. Dos solicitudes concurrentes de cancelación sobre el mismo trabajo deberán producir un estado final coherente y respuestas comprensibles para ambos clientes.
- RF-27. Una solicitud duplicada o reenviada no deberá crear estados contradictorios; el equipo deberá documentar la semántica elegida para identificar o tratar duplicados.
- RF-28. Si un cliente se desconecta durante una solicitud, el servicio deberá conservar un estado coherente y documentar si la operación fue aceptada, rechazada o quedó sin efecto.
- RF-29. Si un proceso hijo termina inesperadamente, el servicio deberá detectar el evento, liberar sus recursos y registrar un estado terminal con información de diagnóstico.
- RF-30. Si un trabajo no termina después de la solicitud normal de cancelación, el sistema deberá aplicar una política de escalamiento documentada y verificable.

## Decisiones funcionales obligatorias
Antes de implementar, el equipo deberá establecer y documentar la semántica de los siguientes comportamientos:
- Capacidad máxima de la cola y respuesta ante saturación.
- Tratamiento de solicitudes duplicadas.
- Resultado de trabajos en cola y en ejecución después de reiniciar el servicio.
- Política de cancelación, tiempo de espera y escalamiento.
- Retención y eliminación de resultados.
- Soporte para múltiples clientes simultáneos.

Estas decisiones podrán variar entre equipos, pero deberán ser consistentes con los RF/RNF, estar registradas en ADR y contar con pruebas de aceptación.
