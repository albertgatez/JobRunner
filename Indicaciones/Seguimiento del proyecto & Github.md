## Aviso importante sobre el seguimiento del proyecto - GitHub -
Les recuerdo que GitHub no será solamente el lugar donde suban el proyecto al final. El repositorio y todo lo registrado en él serán la evidencia principal para respaldar su avance, sus aportaciones y, por lo tanto, la evaluación de su trabajo continuo, colaborativo e individual.

La idea es que podamos ver cómo fue avanzando realmente el proyecto: qué hizo cada integrante, qué decisiones tomaron, qué problemas encontraron, cómo los resolvieron y cómo revisaron el trabajo de sus compañeros. Por ello, no es válido concentrar todo o la mayor parte del trabajo durante los días previos a una entrega.

Cada integrante deberá trabajar en su propia rama y realizar sus propios commits. Esto también aplica para cambios de documentación, diseño, pruebas y verificación; no solamente para el código.

Todo lo registrado en GitHub será verificable y servirá como evidencia de participación. Si una actividad, avance o aportación no aparece reflejada en el repositorio, será difícil considerarla como parte del trabajo realizado.

## Issues y seguimiento en GitHub Projects

El trabajo del proyecto deberá organizarse mediante issues conectados a GitHub Projects.

Los issues deberán:

- Corresponder a necesidades reales del proyecto.
- Estar asignados a una persona responsable.
- Repartirse de manera equitativa entre todos los integrantes.
- Mostrar el avance del proyecto y no crearse solamente para cumplir con el requisito.
- Actualizarse y cerrarse conforme se complete el trabajo.

Cada pull request deberá indicar qué issue resuelve. Por ejemplo, si el trabajo corresponde al issue número 12, escriban **Closes #12** en la descripción del pull request. Cuando el cambio sea aprobado e integrado a **main**, GitHub cerrará automáticamente ese issue. Esto permitirá seguir la relación entre la actividad asignada, el trabajo realizado, su revisión y su integración al proyecto. 

De esta manera podremos seguir la secuencia completa:

**Issue asignado → trabajo en una rama personal → commits → pull request → revisión del equipo → merge a main → issue cerrado.**

No se evaluará solamente cuántos issues o commits tiene cada persona. También se revisará que la distribución del trabajo sea razonablemente equitativa y que las aportaciones correspondan con las necesidades y la complejidad del proyecto.

## Revisión de cambios y merge a main

No habrá una sola persona designada para revisar e integrar todos los cambios. La revisión será responsabilidad de todo el equipo.

El procedimiento será el siguiente:

1. La persona responsable de un issue realiza el trabajo en su propia rama.
2. Al terminar, abre un pull request hacia main y lo relaciona con el issue correspondiente.
3. Todos los demás integrantes del equipo revisan el cambio.
4. Cada integrante registra su aprobación en el pull request mediante la opción **Review changes → Approve**. Si encuentra algún problema, deberá solicitar los cambios necesarios.
5. El autor atiende las observaciones y actualiza el pull request.
6. Una vez que todos los integrantes distintos del autor hayan aprobado, cualquiera de ellos podrá realizar el merge a main.

Aunque solamente una persona presione el botón de merge, la aceptación del cambio deberá ser colectiva y las aprobaciones deberán quedar visibles en GitHub.

Si la versión de GitHub que utilizan no permite bloquear automáticamente el merge hasta reunir todas las aprobaciones, deberán respetar este procedimiento de cualquier manera. No deberá hacerse el merge mientras falte la aprobación de alguno de los integrantes.

## Visibilidad del repositorio

Los repositorios podrán mantenerse privados durante el desarrollo y no será necesario agregarme como colaborador.

Para cada presentación de avance, el repositorio deberá hacerse público desde 24 horas antes y permanecer así hasta 48 horas después. Para la entrega final, deberá estar público desde el inicio de la semana de presentaciones y mantenerse público durante una semana adicional. Después podrá volver a configurarse como privado.

Durante esas ventanas se revisará el historial completo del repositorio, incluyendo ramas, commits, issues, GitHub Projects, pull requests, revisiones y contribuciones de cada integrante.

## Presentaciones de avances

Debido al tamaño del grupo, las presentaciones se dividirán entre las sesiones de martes y jueves. Cada equipo recibirá por correo la fecha que le corresponde, por lo que deberán estar atentos a su correo institucional.

Si reciben una fecha diferente a la del resto de su equipo, avísenme cuanto antes para revisar el caso y alinear la fecha de presentación.

En resumen: GitHub será la bitácora del proyecto. Lo que esté registrado ahí será la evidencia que respalde el avance del equipo y la aportación individual de cada integrante.
